# Une architecture pour tester son front-end

**Alexia Souvane · Vendredi 10 novembre · Amphi A**

## Pourquoi les tests du front disparaissent parfois

Alexia Souvane revient sur des projets web et mobiles où les tests unitaires étaient rarement installés de façon durable. Ils peuvent pourtant donner un retour rapide pendant le développement, quand le contexte du changement est encore frais. Pour eux, la difficulté apparaît quand le test dépend à la fois du composant, du stockage et des détails de présentation.

## Découper le code de l’exemple

Elle montre une petite application de tâches. Dans la première version décrite, le composant importe directement le dépôt qui stocke les données. Toute modification de cette implémentation risque d’affecter le composant ou son test. Alexia introduit une interface entre les deux. Le composant dépend du contrat dont il a besoin, et le dépôt concret devient une manière de remplir ce contrat. C’est l’inversion de dépendance appliquée au front.

## Exercer le comportement

En injectant une autre implémentation, le test peut fournir des données prévisibles, effectuer une action puis vérifier le résultat qui compte. Il n’a pas besoin de reproduire la mécanique de stockage du produit pour chaque scénario. Le découpage ne dispense pas de tester les frontières réelles ailleurs, notamment lorsque le risque se situe dans la connexion au stockage ou dans l’intégration des parties.

## Ce que j’en garde

Si un petit changement d’interface oblige à réécrire des tests qui vérifient pourtant le même comportement, examiner d’abord les dépendances du composant et les détails que le test observe.
